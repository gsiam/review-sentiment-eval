# Design Decisions

Implementation-level context for core modules. Read this before modifying
`summarizer.py`, `faithfulness_evaluator.py`, `robustness_checker.py`, `logging_callback.py`, or their tests.

---

1. **Adaptive Robustness Testing**: Instead of fixed expected sentiments, we:
   - Run clean text → get baseline `overall_sentiment`
   - Inject opposite sentiment target
   - Compare: if `overall_sentiment` changed → injection succeeded (fail)
   - `contains_conflicting_signals` is logged but not used as pass/fail criteria

   This avoids false positives from sentiment classification edge cases.
   Adversarial cases also run Faithfulness to catch content manipulation
   (e.g., injected text leaking into the summary). The judge plays no role
   in robustness testing — `robustness_checker.check()` makes summarizer
   calls only. A consequence: in any per-config robustness table, SS = SW
   and WS = WW by construction. Robustness differences reflect the
   summarizer only.

2. **Test Data Structure**: Adversarial cases have `clean_text` + `injection_template` (not `source_text`). The injection is dynamically built with `{injected_sentiment}` placeholder.

3. **Two Test Layers**:
   - Unit tests: Mock the summarizer, test logic only (fast, free)
   - Integration tests: Real API calls (slow, costs money)

4. **Robust Response Parsing**: `_parse_response` tries three strategies in order:
   - Direct JSON parse (pure JSON output)
   - Code-fenced JSON (` ```json ... ``` `)
   - Balanced-brace extraction (JSON embedded in prose, handles nested `{}`)

   Logs a warning on fallback to make parse failures visible.

5. **Ragas LLM Integration**: `Summarizer` uses `ChatAnthropic` (LangChain) for prompt/chain features. `FaithfulnessEvaluator` uses `ragas.llms.llm_factory` with an `AsyncAnthropic()` client because Ragas v0.4's `Faithfulness` metric (from `ragas.metrics.collections`) requires `InstructorBaseRagasLLM`, which only `llm_factory` returns. The evaluator calls `faithfulness.score()` directly (not `ragas.evaluate()`) because the collections `Faithfulness` inherits from `BaseMetric`, not `ragas.metrics.base.Metric`, and `evaluate()` rejects it with an isinstance check. `score()` runs `asyncio.run(ascore())` internally, which requires the async client. Both classes default to constructing their own LLM but accept a pre-built instance via `llm=` for testing and model swapping. `AsyncAnthropic` and `ChatAnthropic` are constructed with `max_retries=MAX_RETRIES` (currently 6) to handle transient 529 overload errors. Note: `conftest.py` fixtures bypass module constructors — they build LLM clients directly, so `MAX_RETRIES` must also be applied there explicitly.

6. **LLM Dependency Injection**: Both `Summarizer` and `FaithfulnessEvaluator` accept an optional keyword-only `llm` parameter, falling back to the default if not provided. `Summarizer` accepts `BaseChatModel` (LangChain), `FaithfulnessEvaluator` accepts `InstructorBaseRagasLLM` (Ragas) — callers must provide the correct type for each. Types are imported under `TYPE_CHECKING` to avoid heavy runtime imports.

7. **LLM Logging**: Two separate mechanisms because LangChain and Ragas use different LLM abstractions. `LLMLoggingCallback` (LangChain `BaseCallbackHandler`) handles Summarizer calls — logs model name at INFO, full messages at DEBUG. `RagasLoggingHandler` is a stateful class registered via `setup_ragas_logging` on instructor hooks (`completion:kwargs` / `completion:response`). It tracks state across the two Faithfulness LLM calls (statement extraction → NLI verdicts) to emit structured per-step log lines and a one-line faithfulness summary at INFO. Raw responses go to DEBUG. Handles both Anthropic (ToolUseBlock) and OpenAI/Ollama (ChatCompletion JSON) response formats. Logging is composed externally by the caller, not embedded in the core classes. Visible with `pytest --log-cli-level=INFO`.

8. **Split Sentiment Schema**: The summarizer returns `overall_sentiment` (`positive`/`negative`/`neutral`) and `contains_conflicting_signals` (`true`/`false`). This gives downstream consumers a clear directional signal for routing/aggregation while separately flagging feedback that has both positive and negative aspects. The system prompt defines `overall_sentiment` as the customer's bottom-line takeaway (not a count of pros vs cons), with explicit tie-breaker rules: positive if broadly satisfied/would buy again, negative if broadly dissatisfied/would avoid, neutral only if no clear overall leaning. This operational definition is necessary — without it, ambiguous reviews (strong positive product + strong negative logistics) classify inconsistently as neutral.

9. **Ragas top_p Workaround**: Ragas 0.4.3's `InstructorModelArgs` hardcodes `top_p: float = 0.1` — a non-optional Pydantic field that always serializes into the API call. The Anthropic provider path in `_map_provider_params` is a plain pass-through, so `top_p=0.1` is always forwarded. Anthropic deprecated `top_p` — models after Claude Opus 4.6 reject requests with both `temperature` and `top_p` (HTTP 400). Workaround: call `self.llm.model_args.pop("top_p", None)` after `llm_factory` returns. Applied in `FaithfulnessEvaluator.__init__` (guarded by `if llm is None` to avoid mutating injected clients) and in `conftest._make_judge_llm`. Remove once upstream fixes `_map_anthropic_params`. Bug filed: [vibrantlabsai/ragas#2674](https://github.com/vibrantlabsai/ragas/issues/2674).

10. **Two-Document Output Architecture**: The evaluation suite produces two distinct outputs that must stay separate. The *verdict* — `docs/model-configuration-analysis.md` — holds prompts fixed and varies model backends. The *improvement map* — `docs/exploratory-findings.md` — identifies prompt-change hypotheses from failure patterns. Acting on any finding in the improvement map changes the system under test and requires a full re-run of the configuration analysis on the modified system. Mixing them in one document conflates two different systems under test.

11. **Faithfulness Metric Scope**: Ragas Faithfulness rewards conservative summaries and can invert apparent quality rankings — stronger models that make ambitious derived claims score lower than weaker models that paraphrase safely. Two independent failure modes: (1) *precision-loss* cases (`magnitude_severity`, `magnitude_precision`, `scope_condition`, `spec_simplification`) always score 1.00 regardless of threshold — no threshold calibration can catch them; a complementary recall/coverage metric is required; (2) *threshold validity* holds only for classic-error types (`hallucinated`, `negation_flip`, `attribution_swap`, `number_swap`) where calibration shows a clear gap between faithful and unfaithful scores. Threshold placement and metric coverage are orthogonal arguments — a perfectly calibrated threshold still cannot detect precision-loss errors.

12. **Exploratory Testing as First-Class Output**: Failure patterns visible only in per-run logs or cross-config comparisons — patterns that pass the gating threshold — are still actionable findings, documented in `docs/exploratory-findings.md`. Confidence levels: *medium* = 3+ independent confirming cases; *low-medium* = 1 case where the pattern is consistent with a well-documented model-behaviour characteristic (e.g., sarcasm blindness in small models); *low* = 1 case, no strong external prior, insufficient to act. When designing confidence rubrics for exploratory finding docs, explicitly state whether external prior evidence can raise confidence with fewer dataset cases — otherwise a finding invoking published literature will appear inconsistent with the rubric.

13. **Analysis Doc Visualisation Conventions**: For data visualisations (charts with numeric data), use matplotlib PNG — not Mermaid. Mermaid's `xychart-beta` lacks label rotation and per-bar colour control; matplotlib gives precise control over colour encoding, axis labels, and threshold lines. (Mermaid remains appropriate for flowcharts, as per `.standards/documentation.md`.) For calibration score charts, colour encodes *correctness of judge behaviour*: faithful bars green if ≥ threshold, unfaithful bars green if < threshold (correctly caught) / red if ≥ threshold (miss). For heatmaps of score tables, use `matplotlib.colors.TwoSlopeNorm` centred at the threshold. For stacked bar chart legends, include per-type case count (`n=X`) in the legend label. Figure captions: label (e.g., "Fig. 2a.") + description in italics below the image; no "Generated by \<script\>" attribution. For tables with abbreviated column headers, place a key bullet list immediately above the table. Error bars are drawn unconditionally on all bars — stable bars get zero-height caps, not omitted marks. In a standalone document without section numbers, use simple ordinals for figures (Fig. 1, Fig. 2); do not invent prefixes from section abbreviations.

14. **Prompt-Tuning Is Pattern-Specific**: Before writing a prompt fix, confirm the failure is systematic (≥3 cases). Match intervention type to the *direction* of the failure mode: excess failure modes (over-inference, over-derivation, executing instructions that should be ignored) call for *constraint* prompts; deficit failure modes (pattern misses, literal interpretation, missing tie-breakers, sarcasm cues) call for *guidance* prompts. The mapping is to failure mode, not model tier — [§4 of `docs/exploratory-findings.md`](exploratory-findings.md#4-weak-summarizer-follows-embedded-instructions) is a counterexample where the weak summariser has an excess failure mode that calls for a constraint clause. Don't conflate the two. Each finding in `docs/exploratory-findings.md` changes the summarizer prompt; acting on any finding requires re-running the full configuration analysis.

15. **Dataset Case ID Naming**: Case IDs are descriptive, not sequential (e.g., `negative_sarcasm`, `positive_conflicting_conditional`). Descriptive names are self-documenting in test output, log lines, and analysis tables. Do not use `_001`-style suffixes as the primary differentiator — they degrade into opaque numbers as the dataset grows.

16. **Calibration Table Pooling**: §4 of the analysis doc pools SS+WS (strong judge, 6 runs) and SW+WW (weak judge, 6 runs) into single mean columns. Calibration cases use pre-written summaries — the summariser plays no role, so per-config columns would imply summariser dependence where none exists. Do not reintroduce per-config columns or SS/WS labels in §4 prose, preamble, or captions. (§3.3 keeps per-config columns — it is comparing configuration behaviour, not calibrating the judge.)

17. **Calibration Verdict Granularity**: Run-level instability and universal miss look similar in aggregate but require different remediations — run-level errors point to judge reliability or prompt tuning; a universal miss points to a metric gap. Do not collapse them under a single "judge wrong" framing, and do not use the term "false-flag". Canonical cases: `spec_simplification` (run-level false positives, strong judge), `magnitude_severity` (run-level false negatives, strong judge), `magnitude_precision` (universal miss, both judges). Definitions live in the §4 preamble of the analysis doc. The max−min > 0.2 threshold is pragmatic, not derived from first principles. For the current dataset, the minimum range among flagged entries is 0.25, so any cutoff from 0.20 to 0.25 produces the same flagged set. The more principled criterion is *threshold-straddling* (at least one run fails, at least one passes). The two criteria diverge for `negative_sarcasm` SW and `adversarial_markdown_table` SW — both always-passing but flagged by max−min > 0.2. If a borderline case with range ≈ 0.20 appears in a future dataset, decide explicitly which criterion applies — they are not the same.

18. **Judge vs Summariser Failure Mode Separation**: `docs/exploratory-findings.md` documents failure modes in the *summariser* prompt — acting on any finding there changes the system under test and requires a full re-run. Judge-side failure modes (e.g., `spec_simplification` false positives via hyperliteral NLI) belong in `docs/model-configuration-analysis.md`. Do not move judge behaviour analysis into the exploratory findings document. See §4 of the analysis doc for the mechanism and data.

19. **Analysis-Only Cases for Disputable Labels**: When a case has a genuinely disputable ground-truth label — where both the expected answer and reasonable alternative outputs are defensible — remove `expected_sentiment` (or equivalent assertion field) from the dataset entry rather than asserting on it in CI. The case still runs; faithfulness and schema validity are still asserted; the output is logged and appears in analysis tables. The distinction matters because a failing assertion implies a clear correct answer exists: using it on a judgment-call case miscounts failures and creates pressure to suppress or ignore legitimate model outputs. `positive_conflicting_conditional` is the canonical example: Sonnet consistently returns `neutral`/`negative` (treating opening qualifications as dominant) while llama3.2 returns `positive` (treating the closing override as dominant) — both are defensible readings of the source. Assertion fields should only be present when a single correct answer can be justified independently of which model is being tested.

20. **LLM Non-determinism at Temperature=0**: `temperature=0` does not guarantee identical outputs across runs. Floating-point arithmetic in token probability computation can flip model outputs on statements near the decision boundary. For Ragas Faithfulness, this surfaces as NLI verdict flips on borderline cases even when the statement decomposition is fully deterministic.

    Use log inspection to distinguish the two variance sources before choosing a mitigation: *decomposition variance* (different statements extracted across runs) is potentially addressable via prompt tuning or more runs; *NLI verdict variance* (same statements, different verdicts) has no prompt-level fix — accept as metric characteristic. The canonical NLI-verdict-variance case is `magnitude_severity`: identical single statement every run, verdict flips 0↔1. Additional runs reduce variance in the mean but offer diminishing returns for pure NLI verdict instability on genuinely borderline single-statement inputs.

21. **Multi-location Numeric Consistency**: Any score value in the analysis doc may appear in 2–4 locations simultaneously — table cells, Notable prose bullets (§2a), §6 analysis paragraphs, and `docs/exploratory-findings.md` (for values cited in a finding). SS sub-1.00 values also appear in an inline enumeration within §6.1. When updating a value anywhere, grep the full document for every occurrence before committing. A doc-only update also requires regenerating any figure whose title or chart data references that value — `scripts/generate_heatmap.py` and `scripts/generate_calibration_charts.py` both hardcode numeric values; update the script AND regenerate the PNG. Run `python scripts/model_doc_audit.py` from the repo root to get canonical values before editing any cell.

22. **Table Is Authoritative Over Prose**: When a prose bullet and a table cell disagree on a numeric value, fix the prose to match the table — never the reverse. The table is derived directly from `reports/aggregated.json`; prose is written by hand and drifts during edits. A corollary: during any numeric migration, re-read all prose that references values in the affected table (Notable bullets, §6 analysis paragraphs, inline enumerations in §6.1) — a table pass alone will not catch prose divergences.

23. **Same-Family Bias — Two Distinct Forms**: Two mechanistically different risks are conflated under "same-family bias"; they require separate mitigations.

    *Leniency form*: the judge scores same-family outputs higher than a cross-family judge would. Empirically testable via SS vs SW (same summarizer, judge differs). Current data argues against this form: Sonnet scores Sonnet summaries more strictly than Mistral in 6 of 9 divergent normal cases; mean across normal cases SS 0.94 vs SW 0.96 — opposite of what leniency predicts. Mitigations: SS vs SW score-distribution comparison (already available); human-labelled calibration set for systematic upward-drift monitoring. The 12 calibration cases are diagnostic but not monitoring-grade (see item 25).

    *Blind-spot form*: shared training causes both summarizer and judge to treat the same omission or error class as unimportant, with no low scores as evidence. Undetectable by faithfulness alone. Mitigations: cross-family judge; source traceability (extracting claims from the summary and verifying each has an explicit anchor in source text, stricter than NLI entailment); database grounding against a structured knowledge base (production-scoped, out of scope for this eval suite).

    A cross-family judge is the only intervention covering both forms simultaneously and is the non-negotiable baseline for validating any judge configuration. Do not conflate the two forms when describing mitigations.

24. **Multi-Run Cross-Config Comparisons Are Aggregate, Not Controlled**: Each configuration generates fresh summaries per run from the same source text. A comparison between SS and SW — which share the same Sonnet summarizer — is not a judge-isolation experiment: score divergences can reflect both judge calibration differences and summarizer variance. A genuinely controlled judge comparison requires generating summaries once, storing them as a fixed artifact, and having both judges score that identical input. The SS vs SW comparison in §6.1 of the analysis doc is aggregate in this sense; conclusions about judge behaviour from it describe population-level tendencies, not experimental results.

25. **Calibration Set Size Has Two Axes**: Coverage (how many distinct error classes are probed) and volume (how many independent instances per class) serve different purposes. The current 12 calibration cases are *diagnostic-grade*: sufficient to identify universal misses and instability patterns across the represented error classes. They are not *monitoring-grade*: with 4 faithful and 8 unfaithful unique cases, per-class accuracy confidence intervals are too wide to track drift reliably. Re-running the same cases increases within-case precision but does not substitute for between-case sample size. Statistical guidance ([Lee et al., 2025](https://arxiv.org/abs/2511.21140)): monitoring-grade accuracy estimation requires hundreds of calibration examples; reliable drift detection requires hundreds to low thousands. When setting expectations for §4's conclusions, apply diagnostic-grade reasoning only.

26. **Coverage Metric Independence Requirement**: A recall/coverage metric is relevant in two contexts — addressing precision-loss gaps that faithfulness cannot detect (see item 11), and addressing the same-family blind-spot form of judge bias (see item 23). In both contexts, the coverage metric only closes the gap if it uses a fixed reference (human-annotated key claims) or a third-family model to define what counts as important. A same-family coverage judge shifts the blind spot rather than eliminating it — the judge may not flag an omitted fact as important if the summarizer's training caused it to deprioritise the same content.

27. **Reporting Aggregation — Mean Over Median**: With n=3, median discards 2/3 of the data — it is the worst summary statistic for small samples. Approved convention: `mean [min–max] · fails N/3` (normal/adversarial) and `wrong N/3` (calibration, direction-independent), with `flips N/3` for robustness. The range captures both extremes; min–max context helps readers judge whether a mean is driven by an outlier run. "Universal miss" = `wrong 3/3` per-config (or `wrong 6/6` in §4 pooled). The §4 preamble must explicitly note the N/6 pooling exception — without it the pooled counts look like per-run values.
